# RotatingWormholeCollapse

This example evolves GRTresna-produced rotating exotic initial data with the
same CCZ4 + phantom-scalar diagnostics used by `SupportedWormholeCollapse`.
Set `recipe_initial_data_file` in `params_rotating.txt` to a `.gridinit` file
generated by `grteclyn-wrapper/scripts/make_rotating_wormhole_id.py`.

## Implementation Status

The implementation is deliberately GRTresna-first: rotation is introduced as
matter momentum in the elliptic initial-data solve, then GRTeclyn evolves the
solved CCZ4 state from a `.gridinit` file. This avoids starting the rotating run
from a large Hamiltonian/momentum constraint violation.

What has been added:

- `Examples/RotatingWormholeCollapse/` clones the supported wormhole collapse
  diagnostics and matter evolution path.
- `ExternalGridInitialData.hpp` is wired into this example, so
  `recipe_initial_data_file = /path/to/initial_data.gridinit` loads the
  GRTresna output directly.
- `params_rotating.txt` disables the scalar kick:
  `wormhole_phi_perturbation_amplitude = 0.0`. Any non-spherical GW seed should
  come from the solved rotating momentum data, not from an imposed `A_phi`.
- The example builds as an MPI/CUDA executable:
  `main3d.gnu.MPI.CUDA.ex`.
- `grteclyn-wrapper/scripts/make_rotating_wormhole_id.py` writes/runs
  GRTresna configs using the exotic-safe maximal-slicing path:
  `maximal_slicing = 1`, `psi_relaxation = 0.6`, `psi_floor = 0.1`,
  `maximal_jacobian_cap = 25.0`, and indexed scalar lumps.
- `grteclyn-wrapper/scripts/scan_rotating_wormhole_support.py` runs support
  scans with MPI defaults (`--mpi-ranks 8`, GPUs `0..7`).
- `src/visualisation/process_wave/plot_rotating_wormhole_support.py` plots the
  support-threshold scan output.

## Current GRTresna Failure

The new wrapper-generated rotating initial-data cases currently fail inside
GRTresna before producing `InitialDataFinal.3d.hdf5`.

Observed failure:

```text
Running with MPI
...
prterun noticed that process rank N ... exited on signal 6 (Aborted)
```

This happened for:

- a pure rotating exotic quadrupole (`lump0_omega = 0.05`,
  `lump0_mode = 2`, `lump0_exotic = 1`);
- a much smaller rotation (`lump0_omega = 0.005`);
- an axisymmetric exotic control (`lump0_omega = 0.0`,
  `lump0_mode = 0`);
- a boosted exotic control modeled after the committed fixture
  (`lump0_velocity = 0.25`, `lump0_mode = 0`).

Important comparison: the committed fixture
`GRTresna/Examples/ScalarFieldBH/params_exotic_amr_test.txt` did converge with
the same GRTresna executable and MPI environment. That means the installed MPI
stack and the GRTresna binary are usable; the remaining issue is specific to how
the wrapper-generated work directory / params are being run, or to a subtle
solver assumption triggered by those generated inputs.

Most likely causes to check next:

- The wrapper runs GRTresna in a per-case work directory under `GRTeclyn/runs/`,
  while the known-good fixture runs in `GRTresna/Examples/ScalarFieldBH/`.
  There may be a relative-path or Chombo runtime assumption beyond the params
  file itself.
- The generated params are numerically close to the fixture, but output names
  and ordering differ. The solver may be more order/path-sensitive than expected.
- A rotating exotic quadrupole increases the negative kinetic term through
  `Pi`, and can cross the Lichnerowicz/York existence boundary. This explains
  the rotating failures, but not yet the fixture-like boosted control failure.

Recommended next debug step:

1. Copy the exact committed `params_exotic_amr_test.txt` into a fresh wrapper
   work directory and run it through `GRTresnaConfig.solve()` without changing
   any physics values.
2. If that fails, change the wrapper to run the solver from
   `GRTresna/Examples/ScalarFieldBH/` and write outputs to an absolute per-case
   directory.
3. Once the fixture-like wrapper run succeeds, reintroduce rotation gradually:
   first canonical rotating satellite + exotic core, then a weak exotic
   rotating quadrupole.

## Build

```bash
# Production multi-GPU build
make -j 8 USE_CUDA=TRUE USE_MPI=TRUE COMP=gnu CUDA_ARCH=90
```

## Run

**Multi-GPU:**

```bash
# 2 GPUs
CUDA_VISIBLE_DEVICES=0,1 mpirun -n 2 ./main3d.gnu.MPI.CUDA.ex params_rotating.txt

# 4 GPUs
CUDA_VISIBLE_DEVICES=0,1,2,3 mpirun -n 4 ./main3d.gnu.MPI.CUDA.ex params_rotating.txt

# 8 GPUs
CUDA_VISIBLE_DEVICES=0,1,2,3,4,5,6,7 mpirun -n 8 ./main3d.gnu.MPI.CUDA.ex params_rotating.txt
```

**Recommended GPU binding (avoids mapping warnings):**
```bash
mpirun -n 8 bash -c 'export CUDA_VISIBLE_DEVICES=$OMPI_COMM_WORLD_LOCAL_RANK; exec ./main3d.gnu.MPI.CUDA.ex params_rotating.txt'
```

## Generate GRTresna Initial Data

From the repo root:

```bash
uv run python grteclyn-wrapper/scripts/make_rotating_wormhole_id.py \
  --out-dir runs/rotating_wormhole_id \
  --omegas "0.05 0.1 0.2" \
  --amp 0.08 --width 4.0
```

Each accepted case writes `initial_data.gridinit` and `manifest.json`.
Use the gridinit path as `recipe_initial_data_file` in `params_rotating.txt`.

## Restart from Checkpoint

To resume from any checkpoint (for example step **3000** or **4000**):

1. **Rollback** the data directory to the desired checkpoint (use paths matching your clone of this repo and the `output_path` set in `params_rotating.txt`):
   ```bash
   cd /path/to/GRTeclyn
   ./src/scripts/rollback --step 3000 --data /path/to/your/simulation/output
   ```
   (Replace `3000` with the desired checkpoint number, e.g. `4000`.)

2. **Start the watcher** (in a second terminal — use `--not-remove`):
   ```bash
   cd /path/to/GRTeclyn
   ./src/scripts/plot_run.sh --not-remove /path/to/your/simulation/output
   ```

3. **Restart the simulation** using `amr.restart` (this is the correct flag):
   ```bash
   cd /path/to/GRTeclyn/Examples/RotatingWormholeCollapse

   # 2 GPUs example
   CUDA_VISIBLE_DEVICES=0,1 mpirun -n 2 ./main3d.gnu.MPI.CUDA.ex params_rotating.txt \
     amr.restart=/path/to/your/simulation/output/RotatingWormholeChk03000
   ```

> **Tip**: Always replace both the `--step N` in rollback **and** the `ChkN` number in the restart command with the same value (e.g. 4000).
